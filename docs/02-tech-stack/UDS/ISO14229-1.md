# ISO14229-1

# UDS(Unified diagnostic services统一诊断服务)

# Part-1规范与要求

## 1. 简介

ISO 14229 的制定是为了定义诊断系统的通用要求，无论采用何种串行数据链路。

ISO14229基于OSI七层模型为参考而制定，按照该模型进行映射时，诊断测试仪和ECU所使用的服务依据下表被划分到以下各层。

+ 应用层(第7层)：统一诊断服务规定于 ISO 14229-1、ISO 14229-3 UDSonCAN、ISO 14229-4 UDSonFR、ISO 14229-5 UDSonIP、ISO 14229-6 UDSonK-Line、ISO 14229-7 UDSonLIN、其他相关标准以及 ISO 27145-3 WWH-OBD。
+ 表示层(第6层):由车辆制造商规定，以及 ISO 27145-2 WWH-OBD。
+ 会话层服务(第5层):规定于ISO14229-2.
+ 传输层服务(第4层):规定于 ISO 15765-2 DoCAN、ISO 10681-2 FlexRay 通信、ISO 13400-2 DoIP、ISO 17987-2 LIN、ISO 27145-4 WWH-OBD。
+ 网络层服务(第3层):规定于 ISO 15765-2 DoCAN、ISO 10681-2 FlexRay 通信、ISO 13400-2 DoIP、ISO 17987-2 LIN、ISO 27145-4 WWH-OBD。
+ 数据链路层服务(第2层):规定于 ISO 11898-1、ISO 11898-2、ISO 17458-2、ISO 13400-3、IEEE 802.3、ISO 14230-2、ISO 17987-3 LIN 及其他相关标准、ISO 27145-4 WWH-OBD。
+ 物理层(第1层)：规定于 ISO 11898-1、ISO 11898-2、ISO 17458-4、ISO 13400-3、IEEE 802.3、ISO 14230-1、ISO 17987-4 LIN 及其他相关标准、ISO 27145-4 WWH-OBD。

## 2. Scope(范围)

​	ISO 14229 的本部分规定了诊断服务中与数据链路无关的要求，这些服务允许诊断测试仪（客户端）控制车载电子控制单元（ECU，服务器）中的诊断功能，例如连接至嵌入道路车辆中的串行数据链路的电子燃油喷射、自动变速箱、防抱死制动系统等。

​	它规定了通用服务，这些服务允许诊断测试仪（客户端）停止或恢复数据链路上的非诊断消息传输。

​	ISO 14229 的本部分不适用于两个电子控制单元（ECU）之间在车辆通信数据链路上的非诊断消息传输。然而，ISO 14229 的本部分不限制在 ECU 中实现车内车载测试仪（客户端），以便利用车辆通信数据链路上的诊断服务来执行双向诊断数据交换。

​	ISO 14229 的本部分不规定任何实现要求。

## 4. 惯例

​	本部分14229基于OSI服务约定中讨论的适用于诊断服务的各项约定。

​	这些约定规定了服务用户和服务提供者之间的交互。信息通过服务原语(service primitives)在服务用户和服务提供者之间传递。服务原语可携带参数。

​	服务与协议之间的区别如下图所示。

![image-20261008203155284](ISO14229-1.assets/屏幕截图 2026-10-08 222437.png)

​	ISO的本部分定义了确认服务和非确认服务。

​	确认请求包括六种服务原语：request（请求）、req_confirm（请求确认）、indication（指示）、response（响应）、rsp_confirm（响应确认）和 confirmation（确认）。

​	非确认服务仅使用 request（请求）、req_confirm（请求确认）和 indication（指示）这三种服务原语。

​	对于 ISO 14229 本部分中定义的所有服务，请求（request）和指示（indication）服务原语始终具有相同的格式和参数。因此，对于所有服务而言，响应（response）和确认（confirmation）服务原语（req_confirm 和 rsp_confirm 除外）始终具有相同的格式和参数。在本国际标准中定义服务原语时，仅列出请求和响应服务原语。

## 6.应用层服务

### 6.1概览

​	应用层通常称为诊断服务。应用层服务用于客户端-服务器的系统，用于执行车载服务器的测试、检查、监测或诊断等功能。客户端（通常称为外部测试设备）使用应用层服务，请求在一个或多个服务器中执行诊断功能。服务器（通常是 ECU 中的一项功能）使用应用层服务，将所请求诊断服务提供的响应数据发送回客户端。客户端通常是车外测试仪，但在某些系统中也可以是车载测试仪。应用层服务的使用与客户端是车外测试仪还是车载测试仪无关。同一车辆系统中可以有一个以上的客户端。

​	诊断应用层的服务访问点提供若干服务，这些服务都具有相同的总体结构。对于每项服务，均规定了六种服务原语：一种服务请求原语，由诊断测试仪应用中的客户端功能使用，用于将关于所请求诊断服务的数据传递给诊断应用层；

+ a service request primitive服务请求原语:由诊断测试仪应用中的客户端功能使用，用于将关于所请求诊断服务的数据传递给诊断应用层
+ a service request-confirmation primitive服务请求确认原语:由诊断测试仪应用中的客户端功能使用，用于指示在服务请求原语中传递的数据已成功发送到诊断测试仪所连接的车载通信总线上。
+ a service indication primitive服务通知原语:由诊断应用层使用，用于将数据传递给ECU诊断应用或服务器的功能
+ a service response primitive服务回复原语:由 ECU 诊断应用中的服务器功能使用，用于将**所请求诊断服务**提供的**响应数据**传递给诊断应用层；
+ a service response-confirmation primitive服务回复确认原语:由 ECU 诊断应用中的服务器功能使用，用于指示在服务响应原语中传递的数据已成功发送到 ECU 接收诊断请求的车载通信总线上；
+ a service confirmation primitive服务确认原语:由诊断应用层使用，用于将数据传递给诊断测试仪应用中的客户端功能。

​	对于给定服务，请求确认原语和响应确认原语始终具有相同的服务数据单元。这些服务原语的目的是指示较早的请求或响应服务原语调用的完成。本国际标准中的服务描述不会使用这些服务原语，但数据链路特定的实现文档可能会使用它们来定义例如服务执行参考点（例如，当响应完全传输到客户端时，ECUReset 服务将调用复位，这一点通过服务响应确认原语在服务器中指示）。

### 6.2 应用层服务的格式描述

​	应用层服务可以有两种不同的格式，具体取决于车辆诊断系统的配置方式。应用层服务的格式由参数 **A_Mtype** 控制。

​	如果车辆系统的配置使得客户端可以通过使用 **A_SA** 和 **A_TA** 地址参数来寻址所有服务器，则应使用应用层服务的**默认格式**。这意味着 **A_Mtype = diagnostics**。

​	如果车辆系统的配置使得客户端除了 **A_SA** 和 **A_TA** 地址参数之外还需要地址信息，以便能够寻址某些服务器，则应使用应用层服务的**远程格式**。这意味着 **A_Mtype = remote diagnostics**。

应用层服务的不同格式在 **6.3** 中规定。

### 6.3 服务原语的格式描述

明确了应用程序和应用层之间如何交互

#### 6.3.1 一般定义

​	所有应用层服务都具有相同的总体格式。服务原语按以下形式书写：

​			`service_name.type (
​			parameter A, parameter B, parameter C
​			[,parameter 1, ...] )`

+ service_name:诊断服务的名称
+ type:服务原语的类型(如request)
+ "parameter A,......":该参数是 A_SDU（应用层服务数据单元），即由服务原语传递的值列表（寻址信息）
+ "parameter A,parameter B,parameter C"是强制参数，应包含在所有服务调用中；
+ "[,parameter 1,...]"是取决于具体服务的参数（例如，parameter 1 可以是 DiagnosticSessionControl 服务的 diagnosticSession）。方括号表示参数列表的这一部分可以为空。

#### 6.3.2 服务请求和服务指示原语(request和indication)

请求原语由诊断测试仪应用中的客户端功能使用，用于发起服务，并将关于所请求诊断服务的数据(应用程序层)传递到应用层。

![image-20261009214022000](ISO14229-1.assets/image-20261009214022000.png)

指示原语由应用层使用，用于指示一个对 ECU 诊断应用有重要意义的内部事件，并将关于所请求诊断服务的数据传递给 ECU 诊断应用的服务器功能(应用层传给应用程序)。

![image-20261009214219146](ISO14229-1.assets/image-20261009214219146.png)

​	特定应用层服务的请求原语（request primitive）和指示原语（indication primitive）始终具有相同的参数及参数值。这意味着，当数据从客户端传输到服务器端时，应用层中相互通信的对等协议实体不得更改各个参数的取值。在客户端应用程序调用服务请求时，客户端函数传递给应用层的参数值，必须与服务器端诊断应用程序中的服务器函数通过对等应用层的服务指示所接收到的参数值完全相同。

#### 6.3.3 服务响应和服务确认原语(response和confirm)

​	响应原语由 ECU 诊断应用中的服务器功能使用，用于发起服务，并将所请求诊断服务提供的响应数据(应用程序层)传递给应用层。

![image-20261009220636306](ISO14229-1.assets/image-20261009220636306.png)

​	确认原语（confirm primitive）由应用层使用，用于向诊断测试仪应用程序中的客户端函数指示一个对客户端应用程序具有重要意义的内部事件，并传递与先前某个服务请求相关的结果。它并不一定表示远端对等接口发生了任何活动，例如：当服务器不支持所请求的服务，或者通信中断时。

![image-20261009221004201](ISO14229-1.assets/image-20261009221004201.png)

​	特定应用层服务的响应原语（response primitive）和确认原语（confirm primitive）始终具有相同的参数及参数值。这意味着，当数据从服务器传输到客户端时，应用层中相互通信的对等协议实体不得更改各个参数的取值。在 ECU 诊断应用程序中，服务器函数调用服务响应时传递给应用层的参数值，必须与诊断测试仪应用程序中的客户端函数通过对等应用层的服务确认所接收到的参数值完全相同。

对于每一种响应原语和确认原语，都将定义两种不同的服务数据单元（即两组参数）。

- 如果 ECU 中的服务器函数能够成功执行所请求的诊断服务，则应使用第一种服务数据单元，即肯定响应（positive response）和肯定确认（positive confirm）原语。
- 如果 ECU 中的服务器函数执行所请求的诊断服务失败，或者未能在规定时间内完成该服务，则应使用第二种服务数据单元，即否定响应（negative response）和否定确认（negative confirm）原语。



#### 6.3.4 服务请求确认和服务响应确认原语(request-confirm和response-confirm)

​	请求确认原语（request-confirm primitive）由应用层使用，用于向客户端应用程序指示一个对其具有重要意义的内部事件，并将与先前某个服务请求相关的**通信结果**传递给诊断测试仪应用程序中的客户端函数。















![image-20261009222915936](ISO14229-1.assets/image-20261009222915936.png)

​	响应确认原语（response-confirm primitive）由应用层使用，用于向服务器应用程序指示一个对其具有重要意义的内部事件，并将与先前某个服务响应相关的通信结果传递给 ECU 应用程序中的服务器函数。

![image-20261009222954741](ISO14229-1.assets/image-20261009222954741.png)

### 6.4 服务数据单元规范(A_SDU)

#### 6.4.1 强制参数(Mandatory parameters)

##### 6.4.1.1 一般定义

​	应用层服务包含三个必备参数。以下参数定义适用于本国际标准中规定的所有应用层服务（包括标准格式和远程格式）。

##### 6.4.1.2 A_Mtype,应用层消息类型

+ 类型：枚举类型

+ 范围：诊断，远程诊断

+ 描述：参数 **Mtype** 应用于标识 **6.2** 中规定的车辆诊断系统的格式。ISO 14229 的本部分为该参数规定了两个取值：如果 **A_Mtype = diagnostics**，则 **service_name** 原语应由参数 **A_SA**、**A_TA** 和 **A_TAtype** 组成。

  如果 **A_Mtype = remote diagnostics**，则 **service_name** 原语应由参数 **A_SA**、**A_TA**、**A_TAtype** 和 **A_AE** 组成。

##### 6.4.1.3 A_SA,应用层源地址

+ 类型:两字节无符号整数值

+ 范围:0x0000-0xFFFF

+ 描述:参数 **SA** 应用于编码客户端和服务器标识符。

  ​	对于服务请求（以及服务指示），**A_SA** 表示已请求该诊断服务的**客户端功能**的地址。每个请求诊断服务的客户端功能都应使用一个 **A_SA** 值来表示。如果在同一诊断测试仪中实现了多个客户端功能，则每个客户端功能都应具有自己的**客户端标识符**以及相应的 **A_SA** 值。

  ​	对于服务响应（以及服务确认），**A_SA** 表示已执行**所请求诊断服务的服务器功能**的地址。服务器功能可以仅在一个 **ECU** 中实现，也可以分布实现在多个 **ECU** 中。如果服务器功能仅在一个 ECU 中实现，则它应仅用一个 **A_SA** 值来编码。如果服务器功能分布实现在多个 ECU 中，则各个服务器功能地址应针对每个单独的服务器功能各用一个 **A_SA** 值来编码。

  ​	如果远程Client或Server是某条消息的原始源，那么 `A_SA` 表示本地服务器，即承担远程网络与主网络之间网关功能的服务器。

+ 注意: 若请求消息采用物理寻址，则响应消息中的 A_SA 值将与相应请求消息中的 A_TA 值一致。

**如何理解**：A_SA的值不是固定的，针对服务请求(request),其表示已经请求该服务的Client的地址。针对服务响应(response),其表示执行所请求服务的Server的地址。

##### 6.4.1.4 A_TA,应用层目的地址

+ 类型:两字节无符号整数值

+ 范围:0x0000-0xFFFF

+ 描述:参数 **A_TA** 应用于编码客户端和服务器标识符。

  ​	在诊断中规定了两种不同的寻址方法:**物理寻址 和 功能寻址**。因此一个车辆系统可以定义两套独立的目标地址，分别用于每种寻址方法。

  ​	**物理地址**应始终是发送给在单个 ECU 中实现的服务器的专用消息。当使用物理寻址时，通信是客户端与服务器之间的点对点通信。

  ​	**功能地址**如果客户端不知道应对诊断服务请求作出响应的服务器功能的物理地址，或者该服务器功能是作为分布式功能在多个 ECU 中实现的，则客户端使用功能寻址。当使用功能寻址时，通信是从客户端到在一个或多个 ECU 中实现的服务器的广播通信。

  ​	对于服务请求（以及服务指示），**A_TA** 表示应执行所请求诊断服务的服务器的服务器标识符。如果正在寻址的是远程服务器，则 **A_TA** 表示作为从主网络到远程网络之网关的本地服务器。

  ​	对于服务响应（以及服务确认），**A_TA** 表示最初请求该诊断服务、并应接收所请求数据的**客户端功能**的地址（即请求中的 **A_SA**）。服务响应（以及服务确认）应始终使用**物理寻址**。如果正在寻址的是远程客户端，则 **A_TA** 表示作为从主网络到远程网络之网关的本地服务器。
  
+ 注意:响应消息中的 A_TA 值将与相应请求消息中的 A_SA 值一致。

##### 6.4.1.5 A_TA_Type,应用层目的地址类型

+ 类型:枚举

+ 范围:physical,functional

+ 描述:参数 **A_TA_type** 是 **A_TA** 参数的扩展。它用于表示消息传输所选择的寻址方法。

##### 6.4.1.6 A_Result

+ 类型:枚举

+ 范围:ok,error

+ 描述:参数 **A_Result** 由 **req_confirm** 和 **rsp_confirm** 原语使用，用于指示消息是否已正确传输（**ok**），或者消息传输是否未成功（**error**）。

##### 6.4.1.7 A_Length

+ 类型:四字节无符号整数

+ 范围:0d – (2^32-1)d

+ 描述:该参数包含要发送/接收的数据长度。

##### 6.4.1.8 A_Data

+ 类型:字节串

+ 范围:无

+ 描述:该参数包含由更高层实体交换的所有数据。

#### 6.4.2 车辆系统需求

​	车辆制造商应确保系统中的每个server都具有唯一的服务器标识符。车辆制造商还应确保系统中的每个client都具有唯一的客户端标识符。

​	车辆系统中诊断网络的所有客户端地址和服务器地址应编码到相同的源地址范围内。这意味着，在给定的车辆系统中，客户端和服务器不得由相同的 **A_SA** 值来表示。

​	server的物理目标(Physical Address,用于寻址server的地址)地址(A_TA)应始终与该服务器的源地址(Server的A_SA)相同。

​	远程服务器标识符可以独立于主网络上的客户端标识符和服务器标识符进行分配。

​	通常，只有被寻址的服务器应响应客户端请求消息。

#### 6.4.3 可选参数-A_AE,应用层远程地址

+ 类型:2字节无符号整数

+ 范围:0x0000 – 0xFFFF

+ 描述:**A_AE** 用于扩展可用的地址范围，以编码客户端和服务器标识符。**A_AE** 应仅用于实现了**本地服务器**和**远程服务器**概念的车辆中。远程地址表示其自身的地址范围，并且独立于主网络上的地址。

  ​	参数 **A_AE** 应用于编码远程客户端和服务器标识符。根据携带 **A_AE** 的消息的传输方向，**A_AE** 既可以表示远程目标地址，也可以表示远程源地址。

  ​	对于由主网络上的客户端发送的服务请求（以及服务指示），**A_AE** 表示应执行所请求诊断服务的服务器的**远程服务器标识符**（**远程目标地址**）

  ​	**A_AE** 既可以用作**物理地址**，也可以用作**功能地址**。对于 **A_AE** 的每个取值，**系统构建者**应规定该值表示的是**物理地址**还是**功能地址**。

  ​	注意：没有一种特殊参数，能够像 **A_TA_type** 为 **A_TA** 指定寻址方法那样，来表示物理远程地址或功能远程地址。物理远程地址和功能远程地址共享同一个 **1 字节**取值范围，每个取值的含义应由**系统构建者**定义。

  ​	对于由远程服务器发送的服务响应（以及服务确认），**A_AE** 表示已执行所请求诊断服务的远程服务器的**物理位置**（**远程源地址**）

  ​	远程服务器可以仅在一个 ECU 中实现，也可以分布实现在多个 ECU 中。如果远程服务器仅在一个 ECU 中实现，则它应仅用一个 **A_AE** 值来编码。如果远程服务器分布实现在多个 ECU 中，则远程服务器标识符应针对该远程服务器的每个物理位置各用一个 **A_AE** 值来编码。

## 7. 应用层协议

### 7.1 一般定义

​	应用层协议应始终采用**确认式消息传输**，这意味着对于客户端发送的每个服务请求，服务器应发送一个或多个对应的响应。

​	该规则的唯一例外应是少数几种情况：使用功能寻址，或者请求/指示规定不得生成响应/确认。为了避免系统因大量不必要的消息而负担过重，在少数情况下，即使服务器未能完成所请求的诊断服务，也不应发送否定响应消息。这些例外情况在本规范的相关系目中描述（例如，参见 7.5）。

​	应用层协议应与会话层协议并行处理。这意味着，即使客户端正在等待对先前请求的响应，它也应维持适当的会话层定时（例如，如果需要保持其他服务器中的诊断会话继续进行，则发送 TesterPresent 请求。具体实现取决于所使用的数据链路层）。

### 7.2 协议数据单元规范

**A_PDU**（应用层协议数据单元）直接由 **A_SDU**（应用层服务数据单元）和层特定控制信息 **A_PCI**（应用层协议控制信息）构成。**A_PDU** 应具有以下总体格式：

![image-20261011223043857](ISO14229-1.assets/image-20261011223043857.png)

+ "Mtype,SA,TA,TA_Type,RA,Length"是与A_SDU中所用的参数相同的参数。其中RA表示远程地址
+ “A_Data"是为每个具体应用层服务定义的字节串。A_Data 串应以 A_PCI 开始，随后是该服务规定的来自 A_SDU 的所有服务特定参数。方括号表示参数列表中的该部分可以为空；
+ "Length"决定 A_Data 的字节数；

### 7.3 应用层协议控制信息(A_PCI)

#### 7.3.1 PCI，协议控制信息

​	A_PCI 由两种格式组成。这些格式由 A_PCI 参数第一个字节的值来标识。对于所有服务请求，以及第一个字节不等于 **0x7F** 的服务响应，应适用以下定义：

​							`A_PCI(SI)`

+ SI是参数**服务标识符**；

​	对于第一个字节等于 **0x7F** 的服务响应，应适用以下定义：

​							`A_PCI(NR_SI,SI)`

+ NR_SI是用于标识否定服务响应/确认的特殊参数；
+ SI是参数**服务标识符**；

提示：对于服务 **ReadDataByPeriodicIdentifier**（0x2A，参见 10.5）中定义的周期性数据响应消息的传输，应用层协议数据单元（**A_PDU**）中不存在 **A_PCI**。

#### 7.3.2 SI，服务标识

+ 类型:1字节无符号整数
+ 范围:0x00 – 0xFF，根据下表中的定义。

![image-20261011224849097](ISO14229-1.assets/image-20261011224849097.png)

提示：请求消息的服务标识符与肯定响应消息的服务标识符之间存在一一对应关系，其中 **SI 字节值的 bit 6** 表示服务类型。所有请求消息的 **SI bit 6 = 0**。所有肯定响应消息的 **SI bit 6 = 1**，但 **ReadDataByPeriodicIdentifier**（0x2A，参见 10.5）服务的周期性数据响应消息除外。

+ 描述：**SI** 应用于编码服务原语中所调用的具体服务。每个请求服务应分配一个唯一的 **SI** 值。每个肯定响应服务应分配一个对应的唯一 **SI** 值。

  ​	服务标识符用于在 **A_Data** 数据串中表示服务，该数据串从应用层传递到下层（并从下层返回）。

#### 7.3.3 NR_SI,负响应服务标识符

+ 类型:一字节无符号整数
+ 唯一值:0x7F
+ 描述:参数 **NR_SI** 是用于标识否定服务响应/确认的特殊参数。对于否定响应/确认消息，它应作为 **A_PCI** 的一部分。

提示：**NR_SI** 值与 **SI** 值相协调。为了便于 **A_Data** 的编码和解码，**NR_SI** 值不被用作 **SI** 值。（`NR_SI` 被专门分配了一个固定值 `0x7F`，并且这个值不作为普通的服务标识符 `SI` 使用，这样接收方就可以更容易地区分否定响应和其他诊断报文）

### 7.4 否定响应/确认服务原语

​	每个诊断服务都有一个否定响应/否定确认消息，其消息 **A_Data** 字节按**表 3** 规定。第一个 **A_Data** 字节（A_PCI.NRC）始终是特定的**否定响应服务标识符**。第二个 **A_Data** 字节（A_PCI.SI）应是该否定响应消息所对应的**服务请求/指示消息**中的**服务标识符值**的副本。

![image-20261011231121929](ISO14229-1.assets/image-20261011231121929.png)

提示：A_Data 表示否定响应消息的消息数据字节。

参数 **responseCode** 用于否定响应消息中，以指示诊断服务失败或未能及时完成的原因。其取值定义在 **A.1** 中。

### 7.5 服务响应实现规则

#### 7.5.1 一般定义

​	以下子条款规定了服务器在执行服务时的行为。服务器和客户端应遵循这些实现规则。

| 缩写                           | 描述                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| suppressPosRspMsgIndicationBit | 积极响应抑制位。TRUE = 服务器不得发送肯定响应消息（例外情况参见附录 A.1 中 NRC 0x78 的定义）                                                        FALSE = 服务器应发送肯定或否定响应消息 |
| PosRsp                         | 正响应                                                       |
| NegRsp                         | 负响应                                                       |
| NoRsp                          | 不发送肯定响应消息或否定响应消息的缩写                       |
| NRC                            | 负响应码的缩写                                               |

##### 7.5.3.2 采用物理寻址的客户端请求消息

​	本子条款中规定的服务器响应行为，在每项服务的服务描述中均被引用；这些服务在从客户端接收的**物理寻址请求消息**中支持**子功能参数**。

​	下表展示了采用物理寻址的可能通信方案。

![image-20261012224914188](ISO14229-1.assets/image-20261012224914188.png)						**带子功能参数的物理寻址请求消息与服务器响应行为**

a) .服务器发送肯定响应消息，因为客户端请求中的服务标识符和子功能参数受到支持，并且该请求指示需要响应消息。

b) .服务器发送否定响应消息（例如，**IMLOIF**：消息长度不正确或格式不正确），因为客户端请求中的服务标识符和子功能参数是受支持的，但在处理该子功能期间出现了其他错误（例如，根据请求消息中的服务标识符和子功能参数判断，**PDU 长度**错误）。

c) .服务器发送一条否定响应消息，其否定响应码为 **ROOR**（**requestOutOfRange**，请求超出范围），因为服务标识符和子功能参数受支持，但客户端请求消息中所请求的数据参数均不受支持。

d) .服务器发送否定响应消息，否定响应码为 SNS（serviceNotSupported，服务不支持）或 SNSIAS（serviceNotSupportedInActiveSession，活动会话中服务不支持），原因是客户端请求中指示需要响应消息的服务标识符不受支持。

e) .服务器发送一条否定响应消息，其否定响应码为 **SFNS**（**sub-functionNotSupported**，子功能不支持）或 **SFNSIAS**（**sub-FunctionNotSupportedInActiveSession**，活动会话中子功能不支持），因为服务标识符受支持，但对于带有响应消息指示的客户端请求中的数据参数（如果适用），其子功能参数不受支持。

f) .服务器不发送响应消息，因为客户端请求中的**服务标识符**和**子功能参数**受支持，且该请求带有“不发送响应消息”的指示。

g) .与 b) 中的效果相同（即，会发送一条否定响应消息），因为对于物理寻址请求消息上任何需要发送的否定响应，**suppressPosRspMsgIndicationBit** 都会被忽略。

h) .与 c) 中的效果相同（即，会发送一条否定响应消息），因为对于物理寻址请求消息上任何需要发送的否定响应，**suppressPosRspMsgIndicationBit** 都会被忽略。

i) .与 d) 中的效果相同（即，会发送一条否定响应消息），因为对于物理寻址请求消息上任何需要发送的否定响应，**suppressPosRspMsgIndicationBit** 都会被忽略。

j) .与 e) 中的效果相同（即，会发送一条否定响应消息），因为对于物理寻址请求消息上任何需要发送的否定响应，**suppressPosRspMsgIndicationBit** 都会被忽略。

##### 7.5.3.3 功能寻址的客户端请求消息

​	本子条款中规定的服务器响应行为，在每项服务的服务描述中均被引用；这些服务在从客户端接收的**功能寻址请求消息**中支持**子功能参数**。

下表展示了采用物理寻址的可能通信方案。

![image-20261012231216467](ISO14229-1.assets/image-20261012231216467.png)						**带子功能参数的功能寻址请求消息与服务器响应行为**

针对带子功能的功能寻址客户端请求消息，服务器响应情况说明：

a) .服务器发送肯定响应消息，因为客户端请求中的服务标识符和子功能参数受支持，且该请求带有需要响应消息的指示。

b) .服务器发送一条否定响应消息（例如，**IMLOIF**：**incorrectMessageLengthOrIncorrectFormat**，消息长度不正确或格式不正确），因为客户端请求中的**服务标识符**和**子功能参数**受支持，但在处理该子功能期间出现了其他错误（例如，根据请求消息中的服务标识符和子功能参数判断，**PDU 长度**错误）。

c) .服务器不发送响应消息，因为对于功能寻址的请求消息，否定响应码 ROOR（requestOutOfRange，请求超出范围）始终会被抑制。服务器之所以识别出该 NRC，是因为服务标识符和子功能参数虽然受支持，但客户端请求中所需的某个数据参数不受支持。在这种情况下，suppressPosRspMsgIndicationBit 无关紧要。

d) .服务器不发送响应消息，因为对于功能寻址的请求消息，否定响应码 **SNS**（**serviceNotSupported**，服务不支持）和 **SNSIAS**（**serviceNotSupportedInActiveSession**，活动会话中服务不支持）总是被抑制。这些否定响应码由服务器识别，原因是客户端请求中的服务标识符不受支持。在这种情况下，**suppressPosRspMsgIndicationBit** 不起作用。

e) .服务器不发送响应消息，因为对于**功能寻址请求**，否定响应码 **SFNS**（**sub-functionNotSupported**，子功能不支持）和 **SFNSIAS**（**sub-functionNotSupportedInActiveSession**，活动会话中子功能不支持）总是被抑制。这些否定响应码由服务器识别，原因是：**服务标识符**受支持，但对于客户端请求中的**数据参数**（如果适用），其**子功能参数**不受支持。在这种情况下，**suppressPosRspMsgIndicationBit** 不起作用。

f) .服务器不发送响应消息，因为客户端请求中的**服务标识符**和**子功能参数**受支持，且该请求带有“不发送响应消息”的指示。

**注：**如果使用了否定响应码 **RCRRP**（**requestCorrectlyReceivedResponsePending**，请求已正确接收，响应挂起），则无论 **suppressPosRspMsgIndicationBit** 的值如何，都应给出最终响应。

g) .与 b) 中的效果相同（即，会发送否定响应消息），因为对于任何否定响应，**suppressPosRspMsgIndicationBit** 都会被忽略。即使请求消息采用功能寻址，这一点也同样成立。

h) .与 c) 中的效果相同（即，不发送响应消息），因为对于**功能寻址请求消息**，否定响应码 **ROOR**（**requestOutOfRange**，请求超出范围）总是被抑制。该 ROOR 由服务器识别，原因是：**服务标识符**和**子功能参数**受支持，但客户端请求中所需的某个**数据参数**不受支持。在这种情况下，**suppressPosRspMsgIndicationBit** 不起作用。

i) .与 d) 中的效果相同（即，不发送响应消息），因为对于**功能寻址请求消息**，否定响应码 **SNS**（**serviceNotSupported**，服务不支持）和 **SNSIAS**（**serviceNotSupportedInActiveSession**，活动会话中服务不支持）总是被抑制。这些否定响应码由服务器识别，原因是客户端请求中的**服务标识符**不受支持。在这种情况下，**suppressPosRspMsgIndicationBit** 不起作用。

j) .与 e) 中的效果相同（即，不发送响应消息），因为对于**功能寻址请求消息**，否定响应码 **SFNS**（**sub-functionNotSupported**，子功能不支持）和 **SFNSIAS**（**sub-functionNotSupportedInActiveSession**，活动会话中子功能不支持）总是被抑制。这些否定响应码由服务器识别，原因是：**服务标识符**受支持，但客户端请求中的**子功能参数**不受支持。在这种情况下，**suppressPosRspMsgIndicationBit** 不起作用。

#### 7.5.5 服务器响应行为的伪代码示例

```
SWITCH (A_PDU.A_Data.A_PCI.SI)
{
    // ==========================================
    // 场景 1：包含子功能（Sub-function）的服务
    // ==========================================
    CASE Service_with_sub-function:
        // 检查包含子功能的消息最小长度（SID + Sub-function = 2字节）
        IF (message_length >= 2) THEN
            // 提取子功能参数值（屏蔽 bit 7，获取实际子功能编号）
            SWITCH (A_PDU.A_Data.A_Data.Parameter1 & 0x7F)
            {
                // 测试并准备具体子功能的响应
                CASE sub-function_00:
                    IF (message_length == expected_sub-function_message_length) THEN
                        // [TODO: 执行具体业务逻辑]
                        responseCode = positiveResponse; // 肯定响应，内部 NRC = 0x00
                    ELSE
                        responseCode = IMLOIF;           // NRC 0x13: 消息长度错误或格式无效
                    ENDIF
                    BREAK;

                CASE sub-function_01:
                    // [TODO: 执行具体业务逻辑]
                    responseCode = positiveResponse;     // 肯定响应，内部 NRC = 0x00
                    BREAK;

                // ... (省略中间的子功能) ...

                CASE sub-function_127:
                    // [TODO: 执行具体业务逻辑]
                    responseCode = positiveResponse;     // 肯定响应，内部 NRC = 0x00
                    BREAK;

                DEFAULT:
                    responseCode = SFNS;                 // NRC 0x12: 不支持该子功能
            }
        ELSE
            responseCode = IMLOIF;                       // NRC 0x13: 消息长度错误或格式无效
        ENDIF

        // 提取最高位（bit 7）作为“抑制肯定响应消息指示位”
        suppressPosRspMsgIndicationBit = (A_PDU.A_Data.Parameter1 & 0x80); // 结果为 0x00 或 0x80

        // 判断是否需要抑制肯定响应
        IF ( (suppressPosRspMsgIndicationBit) && 
             (responseCode == positiveResponse) && 
             ("not yet a NRC 0x78 response sent") ) THEN
            suppressResponse = TRUE;   // 设置标志：不发送肯定响应
        ELSE
            suppressResponse = FALSE;  // 设置标志：发送响应
        ENDIF
        BREAK;

    // ==========================================
    // 场景 2：不包含子功能（Sub-function）的服务
    // ==========================================
    CASE Service_without_sub-function:
        suppressResponse = FALSE; // 默认发送响应
        IF (message_length == expected_message_length) THEN
            // 检查 SID 后的数据参数是否受支持
            IF (A_PDU.A_Data.Parameter1 == supported) THEN
                // [TODO: 读取数据并准备响应消息]
                responseCode = positiveResponse; // 肯定响应，内部 NRC = 0x00
            ELSE
                responseCode = ROOR;             // NRC 0x31: 请求超出范围
            ENDIF
        ELSE
            responseCode = IMLOIF;               // NRC 0x13: 消息长度错误或格式无效
        ENDIF
        BREAK;

    // ==========================================
    // 场景 3：不支持的 SI（服务标识符）
    // ==========================================
    DEFAULT:
        responseCode = SNS;                      // NRC 0x11: 不支持该服务
}

// ==========================================
// 统一响应发送处理逻辑
// ==========================================
IF (A_PDU.TA_type == functional && 
    ((responseCode == SNS) || (responseCode == SFNS) || 
     (responseCode == SNSIAS) || (responseCode == SFNSIAS) || 
     (responseCode == ROOR)) &&
    ("not yet a NRC 0x78 response sent")) THEN
    // 抑制否定响应消息
    // [TODO: 不发送响应]
ELSE
    IF (suppressResponse == TRUE) THEN
        // 抑制肯定响应消息
        // [TODO: 不发送响应]
    ELSE
        // 发送否定或肯定响应
        // [TODO: 发送响应]
    ENDIF
ENDIF
```

​	当请求消息采用功能寻址，且需要发送 NRC=RCRRP（请求已正确接收，响应挂起）的否定响应时，如果对收到的请求消息进行 PDU 分析后，最终应返回的是使用 NRC=SNS、SNSIAS、SFNS、SFNSIAS 或 ROOR 的否定响应消息，那么**即使这些否定响应在功能寻址下通常会被抑制，也必须发送该最终否定响应消息**。

#### 7.5.6 使用物理寻址和功能寻址的多个并发请求消息

​	常见的服务器实现中，服务器内只有一个可用的**诊断协议实例**。一个诊断协议实例一次只能处理一个请求。规则是：任何接收到的消息（无论寻址模式是**物理寻址**还是**功能寻址**）都会占用该资源，直到该请求消息被处理完毕（发送了最终响应，或应用调用无需响应）。

**只有两种例外情况需要分别处理：**

+ 保活逻辑由客户端使用，用于使先前已启用的会话在一个或多个服务器中保持活动。**Keep-Alive-Logic** 定义为功能寻址的、**SPRMIB=true** 的有效 **TesterPresent** 消息，并且必须由**旁路逻辑**处理。服务器应确保该特定消息不会“阻塞”服务器的应用层，并且紧随其后的寻址消息能够被处理。
+ 如果服务器支持一个或多个**法规规定的诊断请求**，并且在某个**非法规服务**（例如，增强诊断）处于活动状态时收到了其中一个请求，则应**中止**当前活动服务，启动**默认会话**，并处理该法规规定的诊断服务。如果**编程会话**处于活动状态，则此要求不适用。

关于如何处理多个客户端的更多信息，参见附录 J。

### 9.2 DiagnosticSessionControl (10<sub>16</sub>)service(诊断会话服务)

#### 9.2.1(服务描述)

**DiagnosticSessionControl** 服务用于在一个或多个服务器中启用不同的**诊断会话**。

​	诊断会话会在一个或多个服务器中启用一组特定的诊断服务和/或功能。该服务提供一种能力，使服务器能够报告对已启用诊断会话有效的**数据链路层特定参数值**（例如**定时参数值**）。本文件的使用者应定义每个诊断会话中所启用的服务和/或功能的确切集合。

​	服务器中应始终有且仅有一个诊断会话处于活动状态。服务器在上电时应始终启动默认诊断会话。如果未启动其他诊断会话，则只要服务器保持通电，默认诊断会话就应一直运行。

​	服务器应能够在正常工作条件下以及车辆制造商定义的其他运行条件下（例如，跛行回家运行条件）提供诊断功能。

​	如果客户端请求了一个已经在运行的诊断会话，则服务器应发送肯定响应消息，并表现出图 7 所示的行为；图 7 描述了服务器在会话之间切换时的内部行为。

​	每当客户端请求一个新的诊断会话时，服务器应在新会话的定时参数在服务器中生效之前，发送 **DiagnosticSessionControl** 肯定响应消息。某些情况下可能要求：在发送肯定响应之前就进入新会话，同时保持用于发送响应的旧协议定时。如果服务器无法启动所请求的新诊断会话，则它应以 **DiagnosticSessionControl** 否定响应消息进行响应，并且当前会话应继续（关于服务器和客户端应如何行为的更多信息，参见 **diagnosticSession** 参数定义）。非默认诊断会话（不包括 **programmingSession**）中的诊断服务和诊断功能集合，是 **defaultSession** 中所提供功能的超集，这意味着当切换到任何非默认诊断会话时，**defaultSession** 的诊断功能也可用。会话可以启用车辆制造商特定的服务和功能，这些不属于本文件的范围。

为启动一个新的诊断会话，服务器可能要求满足某些条件。所有这些条件均由用户定义。此类条件的示例如下：

+ 服务器可以只允许具有特定客户端标识符（客户端诊断地址）的客户端启动某个特定的新诊断会话（例如，服务器可以要求只有具有客户端标识符 **F4<sub>16</sub>** 的客户端才能启动 **extendedDiagnosticSession**）。
+ 某些安全条件可能需要得到满足（例如，车辆不得移动，或发动机不得运转）。例如，转换到 **programmingSession** 可能会导致正常功能丧失，因此某些 **ECU** 可能要求车辆处于安全状态。

​	在某些系统中，当启动一个新的诊断会话时，改变通信定时参数是可取的。**DiagnosticSessionControl** 服务实体可以使用适当的服务原语来更改定时参数，如下层所规定的那样，以改变本地节点中的通信定时，并可能改变客户端希望与之通信的节点中的通信定时。

图 7 概述了诊断会话的转换，以及服务器在转换到另一会话时应执行的操作

![image-20261014224202709](ISO14229-1.assets/image-20261014224202709.png)

​									**服务器诊断会话状态图**

**关键点:**

1. **defaultSession：**当服务器处于 **defaultSession**，并且客户端请求启动 **defaultSession** 时，服务器应完全重新初始化 **defaultSession**。服务器应重置在已激活会话期间所有已激活/已发起/已更改的设置/控制。这不包括已编程到**非易失性存储器**中的长期更改。
2. **其他到任何 defaultSession 的转换：** 当服务器从 **defaultSession** 转换到除 **defaultSession** 之外的任何其他会话时，服务器应仅**暂停**那些在 **defaultSession** 期间已通过 **ResponseOnEvent (86<sub>16</sub>)** 服务在服务器中配置的**事件**（类似于在 **non-defaultSession** 处于活动状态期间执行 **stopResponseOnEvent**）。
3. **相同或其他会话：** 当服务器从任何非 **defaultSession** 的诊断会话转换到另一个非 **defaultSession** 的会话（包括当前活动的诊断会话）时，服务器应（重新）初始化该诊断会话，这意味着：
   1. 通过 **ResponseOnEvent (8616)** 服务在服务器中配置的每个事件都应停止；
   2. 安全应重新锁定。安全访问的锁定应重置任何依赖于安全访问解锁的活动诊断功能（例如某个 **DID** 的活动 **inputOutputControl**）；
   3. 新会话中支持且不依赖于安全访问的所有其他活动诊断功能应予以保持。例如，当从一个非 **defaultSession** 转换到另一个或同一个非 **defaultSession** 时，任何已配置的周期调度器都应保持活动，并且 **CommunicationControl** 和 **ControlDTCSetting** 服务的状态不应受到影响，这意味着如果在切换会话的时间点正常通信被禁用，则正常通信应保持禁用。
4. **转换到 defaultSession：** 当服务器从除默认会话之外的任何诊断会话转换到 **defaultSession** 时，服务器应恢复每个已通过 **ResponseOnEvent (86<sub>16</sub>)** 服务在服务器中配置且**事件窗口**仍然有效的**事件**。此外，服务器中应激活已锁定的**安全等级**。默认会话中不支持的任何其他活动诊断功能应被**终止**。例如，任何已配置的**周期调度器**或**输出控制**应被禁用，且 **CommunicationControl** 和 **ControlDTCSetting** 服务的状态应被重置。这意味着，如果在会话切换到 **defaultSession** 的时间点正常通信已被禁用，则应重新启用正常通信。服务器应重置在已激活会话期间所有已激活/已发起/已更改的设置/控制。这不包括已编程到**非易失性存储器**中的长期更改。

### 9.3 ECUReset(11<sub>16</sub>)service(ECU复位服务)

#### 9.3.1 服务描述

### 9.4 SecurityAccess(27<sub>16</sub>) service

#### 9.4.1 服务描述

​	本服务的目的是提供一种途径，用于访问因**安全性（security）**、**排放（emissions）**或**功能安全（safety）**原因而受到**限制访问**的数据和/或诊断服务。向服务器下载/上传例程或数据，以及从服务器读取特定内存位置的诊断服务，属于可能需要安全访问的场景。下载到服务器中的不当例程或数据可能会损坏电子设备或其他车辆部件，或者危及车辆对排放、安全或保密标准的**合规性**。该安全机制采用“**种子（seed）与密钥（key）**”的关系。

一种典型的使用该服务的例子如下：

+ 客户端请求"Seed"
+ 服务端发送"Seed"
+ 客户端发送"Key"(与所接收到的 Seed（种子）相匹配 / 适用于所接收的 Seed)
+ 服务器回复“Key（密钥）”有效，并且将解除自身的锁定状态（自行解锁）。

​	“**requestSeed**”子功能参数值应始终为**奇数**，且同一安全等级对应的“**sendKey**”子功能参数值应等于“**requestSeed**”子功能参数值加一。

​	在任何时刻，只能有一个安全等级处于活动状态。例如，如果与 requestSeed `03₁₆` 关联的安全等级当前处于活动状态，并且测试仪成功发出了解锁与 requestSeed `01₁₆` 关联的安全等级的请求，那么此时应仅解锁由 requestSeed `01₁₆` 关联的安全等级所支持的受保护功能。先前由 requestSeed `03₁₆` 关联的安全等级解锁的任何其他受保护功能应不再处于活动状态。安全等级的编号是任意的，不代表（也不暗示）这些等级之间存在任何关系。

​	客户端应通过发送 **SecurityAccess‘requestSeed’** 服务消息，请求服务器进行“解锁”。服务器应使用 **SecurityAccess‘requestSeed’** 肯定响应消息发送一个“种子（seed）”作为响应。随后，客户端应使用相应的 **SecurityAccess‘sendKey’** 服务请求消息，将一个“密钥（key）”数字返回给服务器作为响应。服务器应将该“密钥”与其内部存储/计算的密钥进行比较。如果两个数字匹配，则服务器应启用（“解锁”）客户端对特定服务/数据的访问权限，并通过 **SecurityAccess‘sendKey’** 服务肯定响应消息来指示这一点。如果两个数字不匹配，则应将其视为一次错误的访问尝试。密钥无效将要求客户端按照**附录 I** 中的规定，从头开始重新发送 **SecurityAccess 'requestSeed'** 消息。有关安全访问处理的更多详细信息在**附录 I** 中规定。

​	如果服务器支持安全访问，但当收到 **SecurityAccess‘requestSeed’** 消息时，所请求的安全等级**已经处于解锁状态**，则该服务器应发送一个 **SecurityAccess‘requestSeed’** 肯定响应消息，且其中的**种子值等于零（0）**。对于当前处于**锁定状态**的给定安全等级，服务器**绝不应**发送全零的种子。客户端应使用此方法，通过检查种子是否非零，来确定服务器针对特定安全等级是否处于锁定状态。

​	在服务器上电/复位后，以及在发生一定次数的错误访问尝试后（见下文进一步描述），服务器在能够对来自客户端的 **SecurityAccess‘requestSeed’** 服务消息做出肯定响应之前，可能需要一个**车辆制造商特定的时间延迟**。如果支持此延迟定时器，则在达到车辆制造商规定次数的错误访问尝试之后，或者当服务器上电/复位且先前执行的 SecurityAccess 服务因单次错误访问尝试而失败时，应激活该延迟。如果服务器支持此延迟定时器，那么在成功执行 **SecurityAccess‘sendKey’** 服务之后，服务器应清除其内部用于指示在上电/复位时调用延迟定时器的指示信息。如果服务器支持此延迟定时器，但无法确定在上电/复位之前先前执行的 SecurityAccess 服务是否已失败，则在上电/复位后该延迟定时器应始终处于活动状态。仅当服务器在上电/复位时处于锁定状态，才需要该延迟。车辆制造商应选择是否支持该延迟定时器。

​	对安全（机制）的访问尝试不应妨碍正常的车辆通信或其他诊断通信。

​	提供安全保护机制的服务器，如果在处于锁定状态时请求了受保护服务，应支持发送拒绝消息。

​	在特定诊断会话期间请求的某些诊断功能/服务可能需要成功完成安全访问序列。在这种情况下，应要求以下服务序列：

+ DiagnosticSessionControl service
+ SecurityAccess service and
+ Secured diagnostic service.

(就是有些服务既需要在特定诊断会话又需要在特定安全等级下才能访问，需要执行上述序列)

对于服务器中已启用的诊断会话（即已启动的会话），允许采用不同的访问模式（accessModes）。

**重要**——服务器和客户端应满足7.5中规定的请求和响应消息行为。
